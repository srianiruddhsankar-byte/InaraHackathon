 # Inara — Project Brief for Claude

## What Inara is
A doctor-in-the-loop lab report platform. Tagline: "One test. Many diseases. Always doctor-approved."
Flow: lab uploads results → system normalises tests → rules flag abnormal values → the same panel is screened for several diseases (doctor's suspected disease FIRST) → trend engine compares with the patient's own history → AI draft report → doctor edits and approves (+ treatment plan) → only then the patient sees a plain-language report → patient can share the record via QR with OTP consent.
Inara also monitors wearable data (heart rate, HRV, SpO2, skin temperature, motion) 24/7, compares it with the person's own baseline, local population data and known disease patterns, asks targeted questions when something looks off, and recommends seeing a doctor or going immediately. It covers MULTIPLE conditions (not one disease). Wearable alerts feed into the existing case workflow (doctor → lab test → analysis → approval → treatment). Early warning, not diagnosis. Wearable data is SIMULATED in the prototype; weather is REAL (Open-Meteo).
This is a HACKATHON PROTOTYPE. Priority: a polished, reliable demo over completeness.

## Non-negotiable rules
- Synthetic data only. Never add real patient data.
- Clinical decision support, NOT diagnosis. Wording in UI: "suggests", "consider", "flag for review". Never "you have X".
- Patients NEVER see AI drafts. Only reports with status "approved" are visible in patient views.
- The doctor's prescription is shown verbatim. Any AI explanation of it is labelled "AI explanation".
- Report versions are append-only: ai_draft → doctor_edited → approved. Never overwrite a version.
- AI-generated text always shows an "AI DRAFT" badge on doctor screens.
- Every page shows a footer: "Prototype · Synthetic data · Clinical decision support, not a diagnosis."

## AI layer
- Layer 1 (built): rules + guideline formulas + trend engine in src/lib — deterministic and explainable.
- Layer 2 (planned): a small trained risk model (logistic regression) trained in Google Colab on a public dataset, exported as JSON weights to src/lib/model/, run in the app, with per-feature contributions (linear SHAP = weight × (value − mean)).
- Layer 3 (planned): an LLM that only rewrites structured findings into plain language, with template fallback.
- The AI analysis takes the patient's previous reports as the baseline plus the new report, and produces an editable draft.
- AI output appears ONLY on doctor screens. Patients see only doctor-approved content.

## Tests tracked (canonical keys)
hba1c (%), fasting_glucose (mg/dL), total_chol, ldl, hdl, triglycerides (mg/dL), creatinine (mg/dL), urine_acr (mg/g), hb (g/dL), wbc (10^3/µL, 4.0–11.0; aliases TLC/WBC/Total WBC; /cumm ÷ 1000), mcv (fL), rbc (million/µL), hct (%, haematocrit — in the seeded reports and the Dengue panel, NOT in the CBC panel; aliases HCT/PCV/Packed Cell Volume/Hematocrit), platelets (10^3/µL; /cumm ÷ 1000), ferritin (ng/mL), ast, alt (U/L), plus ggt, tsh, vitamin_d, vitamin_b12, uric_acid, sodium, potassium, bun, crp.
Qualitative tests (no unit, `qualitative: true` in tests.ts): ns1 (Dengue NS1 antigen) and dengue_igm (Dengue IgM). Results Positive / Negative / Equivocal ("Pos", "POSITIVE", "Reactive", "Detected" → Positive; "Neg", "Non-reactive", "Not detected", and "NR" for these tests → Negative). Stored as a code (Negative 0, Equivocal 0.5, Positive 1) with range { high: 0 }, so Positive/Equivocal flag "high" ("Abnormal" in the lab table). No trends, charts or targets (NUMERIC_TEST_KEYS). A number for a qualitative test, or a word for a numeric one, blocks submit.
Unit conversions: glucose mmol/L × 18 = mg/dL; creatinine µmol/L ÷ 88.4 = mg/dL.

## Medical logic (implement exactly, with unit tests)
- Diabetes (ADA): HbA1c <5.7 normal, 5.7–6.4 prediabetes, ≥6.5 diabetes range. Fasting glucose 100–125 prediabetes, ≥126 diabetes range.
- Kidney: eGFR via CKD-EPI 2021 race-free equation: 142 × min(Scr/κ,1)^α × max(Scr/κ,1)^−1.200 × 0.9938^age × 1.012 [if female]; κ = 0.7 (F) / 0.9 (M); α = −0.241 (F) / −0.302 (M). KDIGO G stages: G1 ≥90, G2 60–89, G3a 45–59, G3b 30–44, G4 15–29, G5 <15. Urine ACR ≥30 mg/g = albuminuria (A2), ≥300 = A3. eGFR decline >5 per year = "rapid decline" (KDIGO).
- Anaemia (WHO): Hb <13 (men), <12 (women). Mentzer index = MCV ÷ RBC: <13 suggests thalassaemia trait, >13 suggests iron deficiency. Recommend "consider Hb electrophoresis" when trait is suggested.
- Liver fibrosis risk: FIB-4 = (age × AST) ÷ (platelets × √ALT). <1.3 low, 1.3–2.67 indeterminate, >2.67 high.
- Lipids: LDL ≥160 high, 130–159 borderline; HDL <40 (M) / <50 (F) low; triglycerides ≥150 high.
- Trends: linear regression slope per year over report dates; deviation of latest value from the patient's own mean of earlier reports; flag "drifting within range" when the trend is significant but the latest value is still normal.

## Wearable module (part 2: condition library, population data, pattern detection)
No alerts, questions or notifications yet (part 3). Every result is a "possible pattern", never a diagnosis.
- conditions.ts — the condition library as DATA: id, name, plainName, summary, signalRules, thresholds (each { value, reason }), minNights, supportingFactors, suggestedLabTests ({ label, testKey?, panelId? } — NS1/IgM are free text), questionIds (from QUESTION_BANK), patientExplanation ("These changes can happen in some infections, including dengue…"), references, prevalenceKey, moreSpecificThan. detect.ts reads every number from here.
- Thresholds (round, each with its reason in conditions.ts):
  - z ≥ 2 = unusual for this person (~1 night in 40 by chance); supporting signs (skin temp, HRV) ±1.5 because they only count alongside HR; ≥ 2 nights because one night can be a bad night; +10 bpm above usual = clinically meaningful (≈ 1 °C of fever); rhythm flattened = day–night HR difference < 70% of usual.
  - Gates: < 7 valid baseline nights or night quality < 60% → "insufficient data" (no judgement).
  - early_infection: night HR z ≥ 2 AND (skin z ≥ 1.5 OR HRV z ≤ −1.5). Watch from night 1; concerning when ≥ 2 nights in a row AND night HR ≥ +10 bpm above usual. Flattened rhythm = supporting factor.
  - dengue_like: skin z ≥ 1.5 on ≥ 2 of the previous 7 nights (WHO: febrile phase 2–7 days), then skin z < 1 (back to usual) while night HR z ≥ 2 and higher than the night before → concerning; temp falling but still raised → watch. Past dengue in the record (pastIllnesses/visit notes) multiplies the z thresholds by 0.75. Ranks above early_infection at the same level (more specific).
  - respiratory: SpO2 ≥ 3 points below usual or < 94% (BTS) with HR z ≥ 1; 1 night watch, ≥ 2 concerning.
  - heat_dehydration: afternoon feels-like ≥ 40 °C (IMD heat-wave criterion) AND HR ≥ 5 bpm above weather-expected → watch; plus the next night HR z ≥ 2 or HRV z ≤ −1.5 → concerning. A hot day the weather explains never triggers anything.
  - high_resting_hr: night HR > 100 bpm (tachycardia) or z ≥ 4, with no skin z ≥ 1.5 in the last 3 nights; 1 night watch, ≥ 2 concerning.
  - poor_recovery: HRV z ≤ −1.5 for ≥ 4 nights with skin |z| < 1.5 and HR z < 2 → watch; ≥ 7 nights concerning.
- population.ts + public/data/population.json (SYNTHETIC, generated by scripts/make-population.mjs): levels Velachery (area) → Chennai (city) → Tamil Nadu (state) → India (national); each holds only consenting people: night resting HR + HRV mean/SD by age band (18-29 … 60+) and sex, monthly prevalence bands (low/moderate/high) per prevalenceKey (dengue high in Chennai Oct–Dec), and `members` (demo patients counted, with their contributed values). filterLevel removes the person themselves and anyone whose populationShare is off (exact mean/SD arithmetic). resolveReference: most local level with ≥ 200 people and ≥ 30 in the age/sex band, else up a level; no area/city → national. Reason text e.g. "Velachery has 38 people — using Chennai city data (1,240 people)." percentile() = normal CDF. prevalenceFor walks up to the nearest level with data.
- detect.ts — detectPatterns({ person, nights, amplitude, weather, population, record, settings, day }) → "insufficient_data" (reason) or ranked patterns at watch/concerning: score 0–1 (watch 0.35 / concerning 0.65 base + up to 0.15 signal strength + 0.05 per supporting factor, max 0.95), evidence ("Night HR 78 vs usual 56 (+22)"), supporting factors, labs, population level, data quality. Ranking: level → more specific → score × prevalence weight (low 1, moderate 1.1, high 1.25). Prevalence only re-orders; it never creates a pattern.
- Karthik timeline (tested): Days 1–7 and 10 insufficient data; 8–25 none (Day 7 heat explained); 26–27 early_infection watch; 28–29 early_infection concerning (Day 29 also dengue_like watch, under "Other"); 30 dengue_like concerning (past dengue + Dengue high in Chennai in October), early_infection concerning below it. Ravi and Arjun: none on all days.
- UI (doctor Wearable tab): PossiblePatterns.tsx (top pattern in full; others under a collapsed "Other possible patterns (n)"; footnote "Possible pattern · not a diagnosis") and LocalComparison.tsx (levels tried, reason, usual + this night's HR percentile among people like them).
